# RosterCore requirements

The initial user specification defines a generic, open-source workforce scheduling engine, independent of industry, AI services, HR vendors and persistent storage. Pharmacy is a reference scenario only. Deliver a runnable product with a C++20 library, CMake, an isolated Google OR-Tools CP-SAT adapter, strict versioned JSON/JSON Schema contracts and a JSON CLI callable from any language.

The domain includes employee types, employees and attribute-based/static groups; WORKING and OFF shifts with arbitrary disjoint civil-time intervals and explicit midnight offsets; calendars, exclusions, ISO weeks, recurring availability and intersecting allowed-shift rules. ABSENT and EXCLUDED are distinct states. Every available employee receives exactly one admissible assignment per planned date. Hard constraints must never be silently softened.

Constraint expressions include cardinality EQ/GE/LE, nested AND/OR and order-independent branch-local REMAINING. Ambiguous expressions must be rejected. Prepare extension points for NOT/IMPLIES and hourly coverage, but reject unimplemented operators. Boolean compilation must distinguish equivalence from implication.

Implement continuous cumulative COUNT fairness with exact rational ideal quotas, historical actual counts and debt = ideal − actual. Support EQUAL, AVAILABILITY_WEIGHTED and CUSTOM_WEIGHTED participation; maximum prefix, sum of prefix and final absolute deviations; explicit priorities and lexicographic optimization. Never reset balances at week/month/year boundaries. Rolling-horizon consolidation preserves actual dated assignments, allows a result prefix and never rewrites history. CONTINUOUS_BALANCED is required; EARLIEST_BALANCE, MINUTES and BURDEN_POINTS remain unsupported until correctly implemented.

Each independently revisioned PlanningPolicy packages one objective, its constraints and references to shared constraints/sets. All active policies constrain one joint solve. Atomic single-policy CREATE/REPLACE imports require structural/semantic validation, reference/version checks, expected revision for REPLACE, dry-run previews, explicit application and objective-change history diagnostics. AI drafts may use unresolved symbolic dependencies, but cannot be activated. Supply an AI authoring guide, grammar, operator catalog, valid/invalid examples, prompt and privacy-conscious context export.

The vendor-neutral HR protocol supports stable source/external/event IDs, revisions, UPSERT/DELETE, idempotency, out-of-order updates, tombstones and snapshot reconciliation. Only approved full-day leave affects planning. Changes must not silently alter published or consolidated work. Partial-day operational handling remains an explicit extension.

The local React/TypeScript/Vite playground and Node CLI adapter must share the core model and validators. Provide simple templates, visual editors for the full scenario, recursive AND/OR constraints, objectives, groups, intervals, exclusions, availability, AI dependency mapping/import previews, HR exchange, calendar results, fairness trajectories, comparison and JSON import/export. No JSON editing should be necessary for the ordinary workflow.

Report VALIDATION_ERROR, MODEL_INVALID, INFEASIBLE, FEASIBLE, OPTIMAL and UNKNOWN truthfully, including engine/backend versions, elapsed time, normalized configuration hash, seed/workers/search parameters, objective values/bounds and lexicographic phase states. Implement an independent assignment/constraint verifier and deterministic mode. Diagnose simple conflicts; do not promise minimal unsatisfiable cores.

Work is organized in exactly four phases, detailed in `PROGRESS.md`: foundations; optimization; AI/HR imports; playground/distribution. Each requires working code, relevant tests and documentation. Acceptance includes 3-person continuous balancing, 14 duties among 5 people (3/3/3/3/2), month boundaries, consecutive horizons, absence/exclusion, intersecting groups, nested logic and REMAINING, infeasibility, multiple priorities, policy revision conflicts/atomicity/drafts, HR replay/correction/deletion, objective history changes, timeouts and unsupported input. Add invariant/property tests, representative measured benchmarks, end-to-end tests and Windows/macOS/Linux CI. Use Apache-2.0 for original code, subject to dependency license obligations.

Optimize development effort for a usable testable product. Avoid unnecessary intermediate polish and token expenditure. Record limitations honestly and leave final product acceptance to the user.
